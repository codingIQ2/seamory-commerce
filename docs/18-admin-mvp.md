# 18. 관리자 운영 MVP

## 목표

8단계는 고객이 주문한 뒤 실제 운영자가 수행하는 상품, 재고, 주문 업무를 구현합니다. 관리자 UI만 숨기는 방식이 아니라 모든 관리자 페이지와 변경 Server Action에서 DB의 `ADMIN` 역할을 다시 확인합니다.

## 화면

| 경로 | 책임 |
| --- | --- |
| `/admin` | 판매 상품, 저재고 옵션, 처리 중 주문, 테스트 누적 매출 요약 |
| `/admin/products` | 상품명·브랜드 검색과 판매 상태 필터 |
| `/admin/products/new` | 상품 기본 정보와 첫 옵션을 하나의 트랜잭션으로 등록 |
| `/admin/products/[productId]` | 상품 수정, 옵션 추가, 재고 조정, 재고 감사 이력 조회 |
| `/admin/orders` | 주문번호·이메일·수령인 검색, 상태·기간 필터 |
| `/admin/orders/[orderNo]` | 주문 스냅샷, 배송지, 허용된 다음 상태, 변경 이력 조회 |

## 권한 경계

- 비로그인 사용자는 로그인 화면으로 이동합니다.
- 일반 회원은 `/forbidden`으로 이동합니다.
- 관리자 Server Action은 화면 접근 여부와 무관하게 `assertAdmin()`을 호출합니다.
- 클라이언트가 보낸 역할이나 현재 재고·주문 상태는 신뢰하지 않고 DB에서 다시 조회합니다.

## 상품과 재고 규칙

- 판매가는 정상가보다 높을 수 없습니다.
- slug와 SKU는 중복될 수 없습니다.
- 판매 이력이 생길 수 있는 상품은 삭제 대신 `ARCHIVED` 상태로 보관합니다.
- 재고는 음수가 될 수 없고, 변경 사유가 반드시 필요합니다.
- 조정 시 `stockBefore`, `stockAfter`, 증감량, 담당 관리자, 사유, 시각을 `InventoryMovement`에 남깁니다.
- 낙관적 버전과 직렬화 트랜잭션으로 동시에 발생한 재고 변경 충돌을 감지합니다.

## 주문 상태 머신

```text
결제 대기 ──→ 결제 완료 ──→ 상품 준비 중 ──→ 배송 중 ──→ 배송 완료
    └ 취소        └ 취소          └ 취소
```

- 화면에는 현재 상태에서 가능한 다음 상태만 표시합니다.
- 서버도 같은 상태 전이 규칙을 검증하므로 임의 요청으로 단계를 건너뛸 수 없습니다.
- 배송 시작 이후에는 취소할 수 없습니다.
- 취소 시 주문 수량을 한 번만 복구하며 복구 기록은 DB 유니크 제약으로 중복을 방지합니다.
- 모든 변경은 이전 상태, 다음 상태, 담당 관리자, 사유, 시각을 `OrderStatusHistory`에 남깁니다.

## 로컬 관리자

`.env`에 아래 값을 넣고 `pnpm db:seed`를 실행하면 해당 이메일의 계정이 생성되거나 관리자 역할로 승격됩니다.

```dotenv
ADMIN_SEED_EMAIL="admin@example.com"
ADMIN_SEED_PASSWORD="replace-with-a-local-test-password"
ADMIN_SEED_NAME="HUKUPUKU Admin"
```

실제 운영 관리자 비밀번호는 저장소나 `.env.example`에 기록하지 않습니다.

## 검증 기준

- 관리자와 일반 회원의 페이지 접근 결과가 다릅니다.
- 상품 등록·수정 및 옵션 추가가 서버 검증을 통과해야 저장됩니다.
- 재고 조정 사유가 없으면 저장되지 않습니다.
- 허용되지 않은 주문 상태 전이는 서버에서 거절됩니다.
- 취소는 배송 전 한 번만 가능하고 재고도 한 번만 복구됩니다.
- 포맷, 스키마, 린트, 타입, 단위 테스트, 프로덕션 빌드를 모두 통과해야 합니다.
